# MCP Apps in Pi

This report covers the interactive Node builds of Pi 1.6.0 and 1.6.1, with the
Apps adapter enabled and a working Chromium installation. The protocol under
review is the stable **2026-01-26** revision of `io.modelcontextprotocol/ui`.
The browser bridge uses the repository's pinned SDK 1.7.5. A newer SDK release
or the draft specification does not change the revision implemented here.
[Published specification](https://github.com/modelcontextprotocol/ext-apps/blob/87bcdc8cb626d214917f7485595169d1540db61d/specification/2026-01-26/apps.mdx)

## What the host does

| Spec area | Behavior in Pi | Evidence |
|---|---|---|
| Client negotiation and discovery | Pi advertises the HTML profile on the connection that runs the originating tool. The adapter accepts the nested resource URI and the deprecated flat form. It reads the matching `ui://` resource on that same client and checks the MIME type. Text and base64 HTML are supported. | The real terminal fixture withholds its tool until negotiation and serves base64 HTML. The upstream clock and Arcade serve independently implemented apps. |
| Tool visibility | The model receives only tools whose visibility includes `model`, including after a catalog refresh. A view can list and request only app-visible tools on its own server. Pi's hidden configuration also applies. App calls recheck the reviewed definition. | Real Pi catalog tests cover direct, deferred and code-mode exposure, pagination and changes. The session fixture attempts a model-only call, then completes an approved app-only call. Only the latter reaches the server. |
| Private results, concurrency and reconnects | Each app receipt belongs to one invocation and one native connection. The view gets the original input, public content, structured content and private result metadata. Model and code-mode results of app-linked tools retain public content. A replacement connection requires a new originating call. | Provider observations, two simultaneous native calls, changed arguments, visibility revocation, and connection replacement are covered in the tests. |
| Transport and sandbox | The host, proxy and view have distinct origins. The sandbox announces readiness, receives the reviewed raw HTML, verifies its digest, then opens the same bytes as a separately served document. It forwards JSON-RPC in both directions and reserves the sandbox notification namespace. The view initializes before the host sends tool data. | Real Chromium and the Pi session fixture exercise this path. The fixture also sends a wire-level ping. |
| CSP and review | Chromium receives a **Content-Security-Policy response header** on the app document. Missing CSP uses the stable restrictive default. Declared connect, resource, frame and base sources affect their respective directives. Pi restricts overly broad and private-network requests. It pins the reviewed bytes and policy, records their SHA-256 and policy, flags common form/password patterns, and allows local hash allowlists and denylists. | Header/default, frame allow/deny, exact reviewed resource, canceled opening, and policy-source tests. The manually verified Arcade game uses a specifically reviewed blob frame. Pi reads the declared resource when the user opens it. The spec permits prefetching before a tool call. |
| Lifecycle | A view can open after a result or through `/mcp-app` while an approved tool is running. It receives complete arguments once, then the result or a cancellation notification. The host requests resource teardown on a normal close and allows up to 1.5 seconds for a reply. A view can request its own teardown. | The real terminal fixture withholds completion until its view receives input. A second run returns an error from the pending server call. Shared browser code handles teardown. |
| Tools and resources | Same-session tool calls, tool listing, resource reads, resource and template listing, and prompt listing use the bound connection. The host forwards supported catalog-change notifications. The user can list and call tools offered by the view with Ctrl+G and inspect the result. | The terminal fixture exercises both directions and verifies a session-specific resource value. A stdio fixture announces changes to all three catalogs and the view checks delivery. |
| Chat and model context | Each message or context change requires review. Approved user messages enter Pi with the user role and start a turn. Context changes stay on the active conversation branch and the latest update from each view is included in future model calls. Text and structured context are supported. An image-capable model can receive reviewed static images. The host decodes and re-encodes them, shows each preview, and asks before sending. | The test provider observes the reviewed image, approved user message and latest selection. The superseded selection and private result stay out of the provider request. |
| Links, downloads and clipboard | A valid HTTP(S) URL opens through the system launcher only after approval. The SDK download request supports embedded content and resource links. It shows filenames and sizes before writing new files in Downloads. An app requesting clipboard write can copy text after a physical gesture and explicit review. | The real terminal test refuses a browser launch and verifies downloaded bytes under an isolated home directory. Unit tests check the approved launcher and clipboard arguments. The test leaves the person's actual clipboard alone. Downloads are an SDK/draft feature beyond the named stable revision. |
| Display, theme and sizing | Inline uses the available width and flexible app height. Fullscreen uses the terminal window. Picture-in-picture is a smaller overlay. An unsupported or unavailable request returns the current mode. Resizing, mode and theme changes update the host context. The view gets light/dark styles, locale, time zone, tool info and requested borders. | All three mode requests run in a real Pi terminal. Cell, PNG, pointer and keyboard paths have regressions. A small terminal can decline picture-in-picture. |
| Logs and origin | Ctrl+L opens the last 50 app log messages in the current view. Control characters are removed and each entry is length-limited. Log contents stay out of the model and the saved session. The Pi session records reviewed CSPs and a bounded per-view count of RPC methods. Arguments and private results are excluded from that audit. A server can request its Pi-specific origin by setting `domain` to the first 32 lowercase hex digits of SHA-256 of its configured server name followed by `.mcp-app.localhost`. Browser storage lasts for the view. | The real terminal fixture opens a private diagnostic and verifies it stays out of the model. The sandbox and request paths are shared by both rendering modes. No hosted OAuth callback or cross-view browser storage is implied by the local origin. |

## Limits and exceptions

- **Builds and modes.** Pi has no public extension hook for filtering its native catalog before registration or for attaching a viewer to the exact MCP client. The adapter checks the native module digest and applies its changes in memory. An unrecognized build or already-loaded unfiltered module disables Apps. Print, JSON and RPC mode do not advertise a terminal viewer. `MCP_APPS_OFF=1` switches the adapter off. This implementation cannot provide its in-TUI guarantees on an unsupported Pi runtime.
- **Tool authorization.** Model-visible calls from an agent-opened view go through Pi's validated nested-tool executor. A slash command lacks that executor and refuses those calls. App-only tools have no model-callable Pi registration. They use their originating MCP client after explicit review of the tool and arguments, including from the slash viewer. Pi's third-party model-tool permission hooks do not run on that path. The adapter cannot promise the same hook coverage for both kinds of call.
- **Streaming.** The extension can expose a running call once Pi has authorized it. Before dispatch, streamed arguments have no verified native server connection or completed tool-permission decision. The adapter omits the optional partial-input notifications at that stage. It sends complete input before the result. A process kill or Chromium crash can prevent the final teardown exchange. A view that never finishes initialization cannot receive a host-initiated teardown request under the protocol’s initialization rule.
- **Devices and content types.** Camera, microphone, geolocation and clipboard reading are denied. The headless terminal view has no device picker or recording indicator. The clipboard integration supports reviewed text writes. Pi's conversation interface accepts text and images. Audio and native MCP resource blocks cannot be delivered to it with their original types. Image review accepts up to three PNG, JPEG, WebP or GIF images and delivers a static PNG up to 768 pixels on its longer side. An already reviewed context image is omitted if the user switches to a text-only model. Downloads can retain original file bytes, subject to a limit of 20 files and 100 MiB per request. The spec makes browser permission grants optional.
- **Optional host context.** Pi supplies the originating tool definition, theme variables and terminal input capabilities. The original JSON-RPC request ID and host-provided web font CSS are omitted. A terminal without touch input reports touch as unavailable.
- **Browser policy and browser identity.** The stable CSP vocabulary describes origins. Accepting a literal `blob:` in a resource's `frameDomains` is an Arcade compatibility choice. It requires opening approval for that server and document, applies only to frames, and is absent from the default. Apps that require dynamic evaluation under the default policy, arbitrary dedicated Internet domains, persistent browser sessions or a public OAuth redirect cannot rely on this renderer.
- **Authentication and platform coverage.** Existing Pi-authenticated MCP connections remain in Pi. The same-session fixture proves connection identity. An isolated loopback HTTP server expires a synthetic bearer token and verifies that Pi refreshes it while retaining the same MCP session. A real identity provider’s browser login, account policy, physical clipboard delivery, and system-browser launch across macOS, Linux and Windows remain separate interoperability checks. Live terminal and gameplay verification here used macOS. The underlying Pi MCP client negotiates core protocol revisions through 2025-11-25. Apps has its own revision.
- **Evidence boundary.** The official MCP conformance repository had no Apps host scenario on the review date. The tests below are project regressions, and the upstream clock and hosted Arcade are independent interoperability checks. The project has no upstream certification result for this adapter. [MCP conformance scenarios](https://github.com/modelcontextprotocol/conformance)

## Verified on November 27, 2026

- All 24 Pi adapter tests passed on each of the two supported Node builds. The shared helper passed 53 tests. The Pi extension and shared browser host both passed TypeScript checking.
- The shared Chromium suite passed 30 checks. An animated nested frame received all 20 clicks after scrolling in each rendering mode. The optional cold-start timing run was skipped because its separate cohort server was offline.
- In a real Pi 1.6.1 terminal, the unmodified upstream clock showed its original timestamp, requested approval to refresh and displayed the new server time. In the hosted Arcade game, terminal input moved the player, fired the pistol, opened the Hangar automap and returned to play in both Kitty graphics and character cells. [Clock and gameplay recordings](README.md)

## Reproduce the checks

Install the repository and helper dependencies as described in the [Pi README](README.md). Run
`npm run typecheck` and `npm test` in this directory. The suite includes a real
stock Pi TUI driven through a POSIX terminal, a local model provider and an MCP
server that records its own requests. It needs Python 3 and Chromium. Its home,
Downloads folder, MCP configuration and model observations are temporary.
Set `PI_APPS_TEST_CLI` to the absolute path to another supported Pi Node CLI
to repeat the run on that version.
